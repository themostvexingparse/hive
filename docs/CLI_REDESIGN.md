# The simpler `hive` interface (design, branch `simple-cli`)

Hive's command line asked too much of new users: about fourteen steps across three or four
terminals before an agent wrote a line, tokens copied between computers by hand, flags for
values Hive already knew, and configuration that had to be uploaded and regenerated by hand.
This document is the plan for fixing that without taking anything away from advanced users.
It is a working document: the [checklist](#rollout) at the end says what is built.

## The idea: a ladder

Tools that are both easy and powerful (git, Docker, kubectl, gh, Claude Code, Terraform,
fly.io) don't choose between the two. They stack **layers**: an easy one on top, deeper ones
for those who need them, and every layer reads and writes the same state, so going deeper
never means starting over. Hive gets five rungs.

| Rung | For | What it is |
|---|---|---|
| 0 | Everyone | `hive` with no arguments: says where you are and the one next step; later a guided setup and a chat with the orchestrator. |
| 1 | Daily use, scripts | Short commands with one grammar: `hive agents add`, `hive approve`, `hive config set`. Every value has a default worked out from context. |
| 2 | Customising | Layered settings files: built-in defaults < `hive.toml` (committed, the whole fleet) < `hive.local.toml` (this computer). `hive config explain` says where a value comes from. |
| 3 | Fleet operators | A declarative fleet file with `hive plan` / `hive apply`, and machines joined with a short code. |
| 4 | Integrators | `hive admin …` (today's exact commands, kept), `hive api` for raw access, hooks on fleet events, `hive-<name>` plugins. |

## Rules

1. **Infer, then ask, and only take flags if you want to.** Hive works a value out from the current
   folder, `hive.toml`, the admin login and the server. If it still needs one and runs in a
   terminal, it asks; in a script, it stops with the exact flag to add.
2. **One grammar.** Groups are nouns with the same verbs (`add`, `list`, `edit`, `rm`); the
   daily actions are short top-level shortcuts (`start`, `status`, `approve`, `watch`).
3. **Help in tiers.** `hive help` shows the everyday commands; `hive help --all` everything.
4. **Same name everywhere.** A setting is `integration.review` in the file, in
   `hive config`, and in `hive config explain`.
5. **Every error ends with the command that fixes it.**
6. **Nothing breaks.** Old commands keep working (`hive admin enroll`, `hive decide`,
   `hive overview`, `hive join` with all its flags); they leave the short help, not the CLI.

## Rung 1: the commands

| Command | Does | Replaces |
|---|---|---|
| `hive` | Where things stand, and the next step | reading the quick start |
| `hive login [--server URL]` | Admin login; asks for the token without echoing it | `hive admin login --server --token` |
| `hive server` | Starts a server; with no token it makes one, saves it, and logs this computer in | the token one-liner plus a login |
| `hive agents add VENDOR [ROLES] [--count N] [--name N] [--elsewhere]` | Creates agents and, by default, sets them up on this computer and offers to log them in. Names default to `<vendor>-<n>`; the first agent is the orchestrator, then programmers. `--elsewhere` prints one short `hive join` line for another computer instead. | `admin enroll` + `join` + the login incantation |
| `hive agents list` | Every agent: roles, state, which are on this computer, login state | `status` (part) |
| `hive agents login NAME` | Opens the agent's CLI to log its account in, with the right settings folder, in any shell | per-shell environment-variable commands |
| `hive agents edit NAME [--roles] [--model] [--permission-mode]` | Changes an agent | `admin roles`, re-`join` |
| `hive agents rm NAME` | Removes an agent from the server and this computer | (nothing; impossible before) |
| `hive agents rotate NAME` | New token; a slot on this computer is updated automatically | a `curl` call |
| `hive join NAME --token T [--server URL]` | Sets up an agent created elsewhere; vendor and clone are inferred | the same, with fewer flags |
| `hive approve [ID]`, `hive reject [ID] [NOTE]`, `hive answer [ID] TEXT` | Answer a decision; the ID is only needed when several are open | `hive decide ID …` |
| `hive config get / set / unset / list / explain` | Read and change settings without opening the file; edits keep its comments | editing by hand |
| `hive doctor` | Checks everything, lists fixes | `hive overview` (kept as an alias) |

**Config sync is automatic.** Commands that talk to the server upload `hive.toml` when it
changed since the last upload, and say so in one line. `hive admin push-config` still works.

## Rung 2: settings

```
built-in defaults < preset < ~/.hive/config.toml < hive.toml < hive.local.toml
                    (named in   (you, every repo    (committed:  (this computer only,
                     hive.toml)  on this computer)   the fleet)   git-ignored)
```

- `hive.toml` is what the server enforces and every agent shares.
- `hive.local.toml` changes only how this computer's Hive works: its daemon's checks shell,
  session limits and so on. It is never uploaded. Slots read it from their clone, so their
  worktrees see it too.
- `hive config set KEY VALUE` writes `hive.toml`; `--local` writes `hive.local.toml`,
  `--user` writes `~/.hive/config.toml`. Values are TOML (`true`, `90`, `["npm test"]`);
  anything else is a string.
- `fleet.preset` (`solo`, `team`, `strict`) is a starting bundle that `hive.toml` overrides;
  the server gets `hive.toml` over its preset, never this computer's own settings.
- `[hooks]` (commands run on fleet events) are read only from this computer's own files.
- `hive config explain KEY` prints the value in force, the layer it came from, and every
  layer's value.

Not built: settings from environment variables. The `HIVE_*` names are already taken by
other things (`HIVE_SERVER_URL`, `HIVE_PROJECT`, …), so a setting like `HIVE_INTEGRATION_REVIEW`
would be ambiguous; `hive config set … --user` covers the same need.

## Rung 3 and later

- **Machines joined with a code** (built, see [MACHINES.md](MACHINES.md)).
  `hive machines invite` prints a short single-use code; `hive join CODE` inside the other
  computer's clone pairs it, and its daemon sets up whatever agents are placed on it. The
  server has `machines`, `pairing_codes` and `placements`. Reusable join keys
  (`hive machines invite --reusable`) pair many computers from scripts. Not built: cloning
  the repository when the computer has no clone yet (`hive join` needs one).
- **A declarative fleet** (built, see [CLI.md](CLI.md#hive-plan-and-hive-apply-the-fleet-as-a-file)).
  `[[agents]]` blocks (`name`, `vendor`, `roles`, `count`, `on`, `model`,
  `permission_mode`) in `hive.fleet.toml`, with `hive plan` (shows the difference) and
  `hive apply`; `hive agents export` writes the current fleet out. The server stays the
  source of truth; the file is applied to it, like `kubectl apply`.
- **Rung 0 chat** (built, see [CLI.md](CLI.md#hive-the-chat-with-the-team)). `hive` opens
  a chat with the orchestrator once the team runs, with decisions as prompts Hive itself
  answers (so only your keypress approves) and slash commands that are the rung 1 commands
  (`/agents add` ≡ `hive agents add`). It talks through `#user`, so it works with the
  orchestrator wherever it runs; the orchestrator's skill tells it to answer there.
- **No generated files to commit** (built). Bundles and permission files generated when
  an agent starts, so a `[permissions]` change never needs `hive init` again.
- **Escape hatches** (built). `hive api METHOD PATH`, hooks on fleet events (in this
  computer's own settings, not `hive.toml`), `hive-<name>` plugins on PATH.

## Rollout

Phase 1, on this branch:

- [x] This document.
- [x] `hive` with no arguments: the next step.
- [x] Help in tiers (`hive help`, `hive help --all`).
- [x] `hive login`; `hive server` makes and saves its own token.
- [x] `hive agents add / list / login / edit / rm / rotate`; the server can remove an agent.
- [x] `hive join` infers the vendor and the clone.
- [x] `hive approve / reject / answer` without an ID.
- [x] `hive config get / set / unset / list / explain`, and `hive.local.toml`.
- [x] Automatic upload of `hive.toml`.
- [x] `hive doctor`.
- [x] Docs: README quick start, Getting started and CLI.md use the new commands;
  CONFIGURATION and PERMISSIONS list the new files and forbidden commands.
- [x] Docs: every guide leads with the new commands; the precise forms are documented as
  such in CLI.md and MACHINES.

Phase 2:

- [x] Machines paired with a one-time code (`hive machines invite`, `hive join CODE`);
  `hive machines` and `hive machines rm`.
- [x] Agents placed on paired machines (`hive agents add … --on M`,
  `hive agents edit … --on M|none`); the machine's daemon claims them (a fresh token from
  the server), sets them up and takes them off again, while it runs.
- [x] Machine tokens reach only `/machines/me/*`; unpairing cuts off the machine's agents too.
- [x] Docs: MACHINES rewritten around the three ways to add agents; CLI, CONFIGURATION,
  SECURITY and PERMISSIONS updated.
- [x] Reusable join keys for automation (`hive machines invite --reusable`, `keys`,
  `revoke`).
- [x] Launch-time bundles and `hive init` asking for the test command (done in phase 3).

Decided while building: a paired machine accepts placements automatically
(`accept_placements = "auto"`, or `"never"`). Pairing is already the owner's consent, and
an "ask" prompt has nowhere to appear while `hive up` streams output.

Phase 3:

- [x] `hive.fleet.toml` with `hive plan`, `hive apply [--prune]` and `hive agents export`.
- [x] Placements carry the slot's model and permission mode, so the file (and
  `hive agents edit`) can set them for agents on other computers.
- [x] `hive init` offers the detected test command (from phase 2's list).
- [x] Launch-time bundles: each launch writes the slot's bundle into
  `~/.hive/bundles/<slot>/` from the installed Hive and the worktree's settings and prompts
  (Codex and agy copy it into their private homes as before); the committed `.hive/agent/` is
  the fallback, and what older Hive versions read. Gemini extensions linked to the committed
  copy are relinked once. Agents' file edits in Hive's own folder are refused.

Phase 4:

- [x] The dashboard's *Agents & computers* dialog: add agents (on a paired computer, or with
  a `hive join` line), change roles, placement and model, remove agents, pair and unpair
  computers. (Its JavaScript is syntax-checked; it hasn't been clicked through in a browser.)
- [x] The rung 0 chat: `hive` (or `hive chat`), `hive next` for the next-step screen.

Phase 5 (escape hatches and the rest of rung 2):

- [x] `hive api`, and `hive-<name>` plugins; neither runs inside an agent's session.
- [x] Presets (`fleet.preset`) and the per-user layer (`~/.hive/config.toml`).
- [x] Hooks on fleet events (`[hooks]`), run by the daemon, from this computer's own files.
- [x] `hive agents rotate` for an agent on a paired computer: it takes the new token itself.
